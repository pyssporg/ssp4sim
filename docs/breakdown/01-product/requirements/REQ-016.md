# REQ-016: Runtime Control and Overrides

The product MUST expose runtime control on the C++, C, and Python embedding surfaces. External access from a separate process is a separate requirement (`REQ-017`).

- **Implementation status:** lifecycle, pause/resume/stop, speed, scheduling of those commands, wait, and the daemon lifecycle/reset are implemented. Variable overrides and the override commands (`set_override`, `clear_override`, `list_overrides`) are planned/deferred and are not in current releases.
- **Lifecycle:** one run is allowed per simulator instance (`Simulator` / `Simulation`); a second `start()` throws. `start` blocks until the run is running or terminal; `pause` and `resume` suspend and continue at a macro-step boundary; `stop` terminates and preserves results up to the last completed macro step; `wait` is idempotent, returns a terminal result, and rethrows failure; `simulate()` is `start()` plus `wait()`.
- **States:** created, initialized, running, paused, stopping, completed, stopped, failed.
- **Terminal precedence:** a terminal outcome (completed, stopped, failed) is monotonic; no later stop or control request changes it. `stop()` is idempotent once stopping or terminal, while `stop()` before the run starts is an error.
- **Pre-run teardown:** the internal teardown path cancels a run that has not started (created or initialized) and yields stopped; a failure before the run starts yields failed.
- **Final time:** a completed run reports the configured end time as its simulation time, published without pacing.
- **Stop during flush:** a stop requested while results are being flushed is still observed, and a flush failure yields failed.
- **Paused commands:** a scheduled command that comes due while the run is paused is applied at the next loop gate while paused, in time order.
- **Speed:** a finite factor `>= 0` sets wall-clock pace (`0` = as fast as possible, `1` = realtime, `> 1` faster, `< 1` slower); it changes timing only, never results.
- **Overrides (planned):** `y = k*x + m` applies to the configured side (input or output) of a Real, Integer, or Boolean variable; integer results round half away from zero and saturate int32; a Boolean result is true when nonzero; the override is applied before that side's value is recorded or passed on, with no promise beyond the configured side. This behaviour is deferred and not in current releases.
- **Scheduling:** `pause`, `stop`, and `set_speed` accept an optional `at` simulation time; without it the command applies at the next macro-step boundary, and with it the command is deferred to the first macro-step boundary at or after that time, so activation granularity is one macro step. Immediate `pause`, `resume`, `set_speed`, and non-terminal `stop` calls block until applied (up to one macro step); calls with `at` post and return immediately. `resume` has no scheduled form. Scheduling of `set_override` and `clear_override` is planned with the deferred override feature.
- **Override targets (planned):** `set_override` and `clear_override` identify a target by the `(side, model, name)` triple, so a client must know the model and variable name; there is no discovery call. The engine validates the target: an unknown model or name is rejected, and `set_override` rejects a type it cannot scale.
- **Read-back:** `RunInfo { state, sim_time_ns, speed, session_id, artifacts }` is the sole public read-back, exposed as C++ `info()`; the C `ssp4sim_simulator_get_info()` (`ssp4sim_run_info` by value; a null handle returns the zero/default record and sets `ssp4sim_last_error()`) and Python `info()` are projections carrying only the state, time, and speed.
- **Use cases:** `UC-011`, `UC-012`, `UC-013`, `UC-015`, `UC-016`; `UC-014` remains a goal without phase-shift semantics.
