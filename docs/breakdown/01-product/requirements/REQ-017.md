# REQ-017: External Runtime Access over a Local Socket

The product MUST provide a local external access surface so a separate process can control and observe the same engine without embedding it, and the engine MUST NOT open a network listener.

- **Implementation status:** the daemon, lifecycle commands, speed, scheduling of those commands, reset/shutdown, and mid-run snapshot/restore are implemented. Override commands (`set_override`, `clear_override`, `list_overrides`) are planned/deferred and are not in current releases.
- **Transport:** `ssp4simd` serves a Unix domain socket (or an equivalent local IPC transport) with owner-only permissions, replaces a stale socket path, refuses to start beside a live server on the same path, and unlinks the socket on clean shutdown and on SIGTERM/SIGINT.
- **Framing:** newline-delimited JSON, one object per line with a 1 MiB message limit; every request carries a protocol version (`"v":1`), an optional correlation `id`, and a string `cmd`; responses echo the `id`, async `snapshot` completion events carry the `id` of the request that produced them, and other events carry none.
- **Commands:** `start`, `pause`, `resume`, `stop`, `state`, `set_speed`, `reset`, `snapshot`, `restore`, and `shutdown` are implemented; `set_override`, `clear_override`, and `list_overrides` are planned/deferred and not in current releases. The control commands expose the `REQ-016` semantics unchanged, including scheduled `at`.
- **Override validation (planned):** `set_override` and `clear_override` identify a target by `(side, model, name)`; the engine rejects an unknown model or name with `unknown_variable`, and `set_override` rejects a type it cannot scale with `unsupported_type`.
- **Override listing (planned):** `list_overrides` returns only overrides active at the current simulation time as `{side, model, name, k, m}`, sorted by side, model, and name; an action scheduled with `at` but not yet activated is not listed.
- **Events:** `state`, throttled `time` progress, terminal `done`, `error`, asynchronous `snapshot` completion, and asynchronous `lifecycle` completion events are pushed to every connected client; `time` events are droppable, the others are not. A `snapshot` event carries the originating request `id` when present, `ok`, `code` (`ok` on success, otherwise `run_ended` or a failure code), `path`, and either `bytes` on success or `error` on failure; it carries no simulation time or model counts. A `lifecycle` event carries `operation` (`reset` or `restore`), `ok`, and either the resulting `state`/`sim_time` or a failure `code` (`reset_failed`/`restore_failed`) plus `error`; it carries no request `id`.
- **Checkpointing:** `snapshot` checkpoints the whole simulation while the run is `Running` or `Paused`. The daemon owns an async snapshot worker and request queue (multiple requests may be queued) and replies `accepted` immediately; the worker calls the blocking `Simulator::snapshot`, which posts one `Snapshot` action through `ControlChannel`; the run loop consumes it at the next macro-step boundary, identically in both states, and one `snapshot` event reports success, path, total file size, and the correlated request `id`. There are no snapshot progress events. When `simulation.snapshot.directory` is configured, `snapshot` and `restore` reject paths outside it (canonicalized, so `..` and escaping symlinks are rejected) with `bad_value`. Every runtime control, including `snapshot` (and future `set_override`), is an `Action` in `ControlChannel`; only the run loop applies it; `start` stays on the poll thread, and `reset`/`restore` drive the public `Simulator` API on the background lifecycle thread without replacing the `Simulator` object; `start` for a `restore` with `start:true` runs on the poll thread after the fresh session is installed, and `shutdown` joins the lifecycle thread before teardown. `reset` replaces the session in place from the original parsed config and discards prior in-memory simulation state. `restore` requires the same SSP content hash; it prechecks `canGetAndSetFMUstate`/`canSerializeFMUstate` before mutating anything, reconstructs FMU state, signal rings, resolver frontiers, and simulation time, and fails all-or-nothing when any FMU lacks that capability. A failed apply is reported as `apply_failed` and the higher-level restore paths keep the old stopped runner. Snapshots are a version-4 `SSP4SNAP` container: a manifest lists self-serialized sections (one per live FMU model plus one resolver-frontier section) over one payload. String-valued signal storage is carried inside the model sections with zeroed binary ranges; invalid UTF-8 or an embedded NUL is `unsupported`. Only the current format version is readable; older versions are rejected. A restored run keeps the prior pace (carried into the fresh control before start) and, with CSV recording enabled, writes a new `<stem>.restored-<uuid><ext>` segment so prior output is preserved. Checkpoint files are build/version specific.
- **Concurrency:** one active simulation per daemon; any connected local client may issue commands; the daemon accepts at most eight clients and serves them from one single-threaded poll loop. A `reset` or `restore` lifecycle job runs on one background lifecycle thread while the poll thread keeps serving `state` (from the `RunInfo` captured when the job began) and `shutdown`; every other command is rejected with `server_busy` until the job completes.
- **Lifecycle:** `reset` and `restore` reply `accepted` and, on the background lifecycle thread, call public `Simulator::shutdown()`/`wait()` when the old run had started, read `info()`, then public `Simulator::reset()` or `Simulator::restore(path, false)`; the `Simulator` object is never replaced. A restore with `start:true` starts on the poll thread after the fresh session is installed, and the daemon reports completion with one `lifecycle` event. A live run's terminal `state`/`done` (and `error` on failure) are emitted before the fresh state, and the snapshot worker is stopped and joined at lifecycle start, settling any queued request as `run_ended`. `reset` resets control state (including overrides once that deferred feature lands); `restore` uses the same lifecycle path before loading a checkpoint, and with `start:false` leaves the restored run initialized and stopped. Failure keeps the previous stopped session and reports `reset_failed`/`restore_failed` in the `lifecycle` event. `shutdown` joins any lifecycle job, stops and waits for a live run, closes clients, unlinks the socket, and exits.
- **Trust boundary:** access is local-host only and relies on filesystem socket permissions; remote authentication and remote clients are not promised.
- **Use cases:** `UC-026`.
