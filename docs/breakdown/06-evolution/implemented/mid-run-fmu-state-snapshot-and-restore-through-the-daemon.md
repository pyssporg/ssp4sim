# Mid-run FMU state snapshot and restore through the daemon

**Purpose:** The implementer planning daemon checkpointing uses this node to accept or reject the one restore path that stays coherent with non-FMU run state; without it the plan restores FMUs alone and resumes on stale signal history.

---

**Question:** Can the daemon snapshot a mid-run simulation to a persistent file and restore it into a fresh runner, and what must accompany FMI state?

**Evidence:** Delivered across the FMI adapter, signal storage, resolver, synchronous core, runner, control, daemon, and the public C++/C/Python surfaces. The v4 file is one little-endian `SSP4SNAP` container with a 28-byte header, a JSON manifest, and a payload that concatenates self-serialized sections in manifest order: one section per live FMU model (identity, current time, FMI 2.0 state blob, and input/output `SignalStorage` sections) plus one resolver-frontier section; the manifest lists each section's kind, model name where applicable, and payload-relative offset/size, and carries the SSP content hash and `sim_time_ns`. The header carries an FNV-1a 64 content checksum over the manifest and payload. String-valued signal storage is carried inside the model storage sections with typed string values and zeroed binary ring ranges; restore reconstructs the `std::string` objects and swaps the saved values in; invalid UTF-8 or an embedded NUL is `unsupported`. Only the current format version is readable; older versions are rejected. Saves write a `<target>.part-<uuid>` temp sibling, fsync it strictly, rename atomically, and attempt a best-effort parent-directory fsync, so a failed save never truncates a good checkpoint. Every snapshot is one blocking `Simulator::snapshot(path)` call, which posts a private `SnapshotWork` (`RunThreadTask`) onto the single time-sorted queue inside `RunControl` and waits on a shared promise; the run worker executes `SimulatorCore::save_snapshot` at the macro-step boundary identically for `Running` and `Paused`, and the queue settles the work as `SnapshotError("run_ended", ...)` when the run ends first. The promise carries the `SnapshotSummary` or the exception, so no snapshot service, result channel, correlation state, drain, or wait accessor lives in the library. `SimulatorCore::save_snapshot`/`load_snapshot` own the format and validation. The daemon owns the async worker, request queue, and request-`id` correlation; the worker is the only caller of the blocking `Simulator::snapshot`. Restore and reset remove and rebuild the runner through `Simulator::rebuild`, which quiesces the old runner through `SimulationRuntime::shutdown` (called by `Simulator::shutdown`). The daemon exposes async `snapshot` (multiple queued requests allowed) and async `reset`/`restore` with a background rebuild; `reset` is a full destroy/rebuild that leaves no per-run state. The public `Simulator` exposes blocking `snapshot`/`restore` plus `reset`; the C ABI and Python expose `snapshot`/`restore`/`reset`. The Dahlquist fixture round-trips, and a restored run reproduces 50 tail rows of the uninterrupted run exactly (tolerance `1e-9`). The CTest suite and the daemon/API Python suites pass. The scenario reference FMU declares no state capability, so its adapter round-trip case takes the skip path.

**Change:** `snapshot {path}` queues a checkpoint while `Running` or `Paused` and always replies `accepted`; the daemon worker completes it and one correlated `snapshot` event reports `id`, `code`, simulation time, file size, and model counts. There are no snapshot progress events. `restore {path,start}` stops and joins, rebuilds on one background lifecycle thread, validates file header, checksum, identity, config, and the section table before mutation, then applies each self-serialized section (FMU state, rings, strings, frontiers) and time last, carries the prior pace into the fresh control, and optionally starts. `reset` uses the same async rebuild path but destroys the old runner and installs a freshly built initialized one, so no per-run state survives. A CSV restore writes a new `<stem>.restored-<uuid><ext>` segment. `simulation.snapshot.directory` restricts daemon paths. Capture is all-or-nothing.

**Risk:** Checkpoints are build/version specific and not portable across FMU builds. A save holds the payload in memory once and writes sequentially; the temp file is fsynced strictly and the parent directory best-effort around the atomic rename, so a crash can leave a stale `<target>.part-<uuid>` file but never a truncated target. A failed apply raises `apply_failed` and leaves the target SimulatorCore unspecified; higher-level restore paths discard the failed instance by building a fresh runner, keeping the old stopped runner. The daemon reads `state` from the old runner while the background lifecycle thread stops it, relying on `RunControl`'s mutex; `Daemon`'s move constructor is safe only before any lifecycle or snapshot thread starts; the server moves it immediately after construction and the snapshot worker starts lazily on the first request. A failed restore or rebuild keeps the previous stopped runner and reports a failure event.

**Acceptance:** Met: round-trip, atomic write, checksum, path-independent content-hash restore, mismatch rejection, mid-run resume to completion, exact continuity, paused capture, request-`id` correlation, path policy, async lifecycle, public C++/C/Python surfaces, and a deterministic `apply_failed` test (a valid-checksum snapshot with a truncated model section makes Dahlquist deserialize fail). Open: payload streaming is one-copy-in-memory rather than per-blob.
