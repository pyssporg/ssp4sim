# Runtime control on the public API and the local control daemon

**Question:** Should the public API gain `start`, `pause`, `resume`, `stop`, `set_speed`, overrides, state, and wait, and should a local daemon expose the same control?

**Evidence:** The C++ `Simulator`, C API, and Python bindings originally exposed only one-shot init/simulate, and `Graph::invoke()` was a tight blocking loop with no interrupt or speed factor. Applied: `RunControl` state machine and run thread, speed-aware macro-step pacing, and the `ssp4simd` NDJSON daemon. Variable overrides were not implemented; the override implementation was deferred to reduce verification load and will be implemented later.

**Change:** Expose the lifecycle, speed, state, and wait operations through C++ (`simulator.hpp`), the C ABI (`simulator_c_api.h`), and Python; `start()` blocks until the run is running or terminal, `info()` returns one coherent `RunInfo { state, sim_time_ns, speed }`, and terminal outcomes are monotonic; keep `simulate()` as `start()` plus `wait()`; add the Unix-domain-socket daemon in `src/public/ssp4sim_server/`. The override operations (`set_override`, `clear_override`, `list_overrides`) and `y = k*x + m` behavior are planned/deferred and are not in current releases.

**Risk:** Medium-high — the first background thread in the simulator layer (races, deadlock, cleanup ordering); lifecycle tests need timing-aware infrastructure. Mitigated by the `RunControl` unit tests, C ABI test, Python control test, and daemon end-to-end test.

**Acceptance:** Implemented: lifecycle, speed, state, and wait behave per spec across all three APIs; `simulate()` is unchanged; stop preserves partial results; the daemon passes its NDJSON and end-to-end suites. Variable overrides are deferred, not implemented, and have no current coverage. Covered by `tests/lib/control/`, `tests/lib/high_level/test_c_api_control.cpp`, `tests/python/high_level/test_runtime_control.py`, `tests/python/test_ssp4simd.py`, and `src/public/ssp4sim_server/test_ndjson.cpp`.
