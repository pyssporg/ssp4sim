# Dependency-ordered FMU initialization for SSPs needing connected inputs at init

**Question:** Should FMU initialization become dependency-ordered so a target FMU exits init with committed upstream outputs instead of its own start values?

**Evidence:** ssp4sim initializes each FMU independently (`executor_base.cpp:25-32`), so connected inputs hold their own start values at `exit_init`. The `signal_init_chain_guard` fixture fails on that ordering and is pinned as a strict xfail (`tests/README.md:181-187`); `signal_init_loop_guard` additionally needs loop-breaking or reload-and-retry that neither ssp4sim nor OMSimulator implements (`tests/README.md:188-196`). A prototype was implemented and reverted (no tests, uncommitted). The start-value patching workaround is scenario-specific.

**Change:** Add `simulation.initialization.order` (`independent` default, `dependency` opt-in); for `dependency`, order models by topological/SCC utilities and per model enter_init, copy committed upstream outputs into inputs, exit_init, and commit the start-time frontier. DAG-only in the first increment; cycles are rejected with a clear error and stay the separate `signal_init_loop_guard` gap.

**Risk:** Moderate — init path, config, and docs; `independent` must stay byte-for-byte compatible, the resolver must be installed before the pass, and `start_time != 0` area/timestamp semantics need tests.

**Acceptance:** The unmodified `signal_init_chain_guard` fixture runs under ssp4sim without patched start values and its xfail is removed; `signal_init_loop_guard` remains an explicit xfail; ordering, loop rejection, and `independent` parity are unit-tested.
